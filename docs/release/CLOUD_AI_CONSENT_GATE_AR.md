# حواجز الخصوصية وموافقات مزودي الخدمات السحابية — المرحلة 3

## التغطية التنفيذية

يستخدم backend مصدراً واحداً لموافقات المستخدم المحددة بالغرض والمزود، ويرفض الإرسال إذا غابت هوية الجلسة أو تعذر قراءة سجل الموافقة أو لم يطابق إصدار السياسة المعتمد. إصدار الكود `cloud-ai-2026-10-v1`، لكن منح الموافقات الجديدة يظل معطلاً ما لم يطابق `MYTWIN_CLOUD_AI_APPROVED_POLICY_VERSION` الإصدار حرفياً. لا تُضبط هذه القيمة قبل مراجعة إفصاح المزودين والاحتفاظ والمعالجة واعتماد سياسة الإصدار.

تغطي الحواجز الآن طلبات AI Gateway وعميل streaming القديم لتوليد النص؛ توليد الصور وتحليلها وتحريرها، بما في ذلك مسار الأفاتار الذي لا يقرأ سمات الذاكرة قبل الموافقة؛ تحويل النص إلى صوت عبر ElevenLabs/Edge TTS؛ تفريغ الصوت عبر Groq/Gemini؛ والـ embeddings السحابية عبر Gemini/OpenAI. كل fallback مزود-محدد، فلا ينتقل الطلب إلى مزود لم يوافق عليه المستخدم. cache embeddings معزول بحسب المالك والمزود، وتُفحص الموافقة قبل استخدامه.

أُضيف أيضاً opt-in موحد للإشعارات الاستباقية: لا ترسل OneSignal أو Expo محتوى استباقياً إلا إذا كان `profiles.push_settings.proactive_enabled` يساوي `true` صراحة. شاشة إعدادات الهاتف تقرأ وتحفظ هذا الخيار من API، والمفتاح الافتراضي المحلي والخادمي هو الإيقاف. هذا الخيار منفصل عن إذن نظام التشغيل وعن موافقات معالجة AI.

## قاعدة البيانات والهوية

تضيف `20261011_p0_cloud_ai_consent.sql` جدول `privacy_consents` بصف لكل user/purpose/provider، وقيود لقيم المزودين والأغراض، وRLS مفعّل/مفروض، ومنع الوصول المباشر للـ anon/authenticated. التطبيق الخلفي يكتب عبر service-role ويستخرج `user_id` من JWT. جدول الموافقات مدرج في جرد تصدير/حذف الحساب، لكن لم يجر إثبات المخطط على staging ولم تُختبر عمليات التصدير/الحذف على قاعدة حية.

مسارات الأفاتار أصبحت تتطلب تطابق مالك الطلب مع هوية bearer token. مسار STT لا يقبل `user_id` من العميل، ويحدد صاحب الطلب من الجلسة، مع حد حجم للصوت. لا يُعتبر ذلك بديلاً عن إكمال عزل كل مسارات API المتبقية في مراحل الهوية وRLS.

## الحالة والقيود

مشروع Supabase الظاهر بالمرجع `nckgqvpocawknhkruhip` كان `INACTIVE` في آخر فحص. لم تُطبق migration ولم تُقرأ بيانات مستخدمين ولم يُجر تعديل على قاعدة فعلية. طبّق التغيير على staging نشط فقط بعد تحديد المشروع ومراجعة الإفصاح؛ لا تشغله على الإنتاج دون تأكيد البيئة وخطة النسخة الاحتياطية والرجوع.

`PRIVACY_POLICY.md` ما زالت مسودة تشغيلية وليست إشعاراً قانونياً معتمداً. تحتاج قائمة مزودي الإنتاج الفعلية وروابط شروط المعالجة ومناطق البيانات والاحتفاظ وموافقة بشرية قبل فتح المنح. أي تغييرات للسياسة تستلزم تحديث `POLICY_VERSION` ثم إعادة مراجعة من المنتج/الخصوصية.

هذه الخطوة لا تنهي جرد جميع الاتصالات الخارجية أو بوابات API. يجب أن يستمر البحث عن أي مزود أو SDK يرسل محتوى مستخدم خارج AI Gateway/المسارات المذكورة، وأن تضاف له موافقة purpose/provider واختبارات egress قبل اعتماد ادعاء الشمول. كما أن تدقيق npm الحالي ما زال يمنع CI؛ لا دمج أو إصدار حتى يصبح CI أخضر بعد ترقية مرحلية متوافقة.

## بوابات الإطلاق

1. تحديد مشروع staging نشط والتأكد من backup وخطة rollback.
2. اعتماد إشعار دقيق يذكر الغرض والمزود والبيانات والاحتفاظ والتحويلات ذات الصلة، ثم اعتماد إصدار السياسة.
3. تطبيق migration على staging فقط والتحقق من RLS/privileges وقيود الـ purpose/provider.
4. اختبار grant/revoke، تبديل المستخدم A/B، سحب الموافقة مع تعطيل منح الجديدة، وexport/delete end-to-end.
5. إتمام جرد egress وتغطية كل provider fallback باختبار يمنع الاتصال عند غياب الموافقة.
6. معالجة audit المتبقي وترقية Expo/React Native تدريجياً، ثم تشغيل CI وE2E على staging قبل أي دمج أو نشر.
