# Soul Sync — Master Architecture Contract

## Product definition

Soul Sync develops infrastructure for persistent, evolving digital entities.
My Twin is the reference implementation.

This document is an engineering contract, not a claim of scientifically
established phenomenal consciousness.

## Non-negotiable invariants

1. One entity.
2. One canonical identity.
3. One authoritative persistent state.
4. One lifecycle.
5. One governed action path.
6. Frontend observes/projects; backend owns truth.
7. Evidence is not an intention command.
8. Emotion-like state is not proof of subjective feeling.
9. A capability is not the entity.
10. External models, runtimes and frameworks remain replaceable.
11. Every state-changing capability follows `Intent → Policy → Action → Result → Memory`.
12. Evolution must preserve continuity and provenance.

## Canonical entity loop

`Evidence → Perception → Interpretation → Experience → Memory → State → Cognition → Motivation → Decision → Constitution → Action → Result → Experience → Memory → Reflection → Learning → Evolution → Identity`

## Ownership boundary

Soul Sync owns:

- Entity identity and Digital Passport
- Self model
- User model
- World model contract
- Experience formation policy
- Memory policy
- Relationship state
- Emotional dynamics model
- Curiosity and motivation policy
- Goals
- Reflection/evolution policy
- Constitution and human authority
- Trust
- Lifecycle/continuity contract
- Provenance and evolution lineage

External projects may implement replaceable infrastructure or capabilities.

## External integration rule

An external dependency must be isolated behind an adapter/protocol and must
not become the authoritative owner of identity, continuity, constitution,
relationship state, or memory policy.

Candidates include temporal knowledge graphs, durable workflow engines,
event infrastructure, model runtimes, browser/computer tools, smart-home
systems, and cognitive-programming/optimization systems.

## Capability rule

A capability must be:

- explicit;
- permissioned;
- policy checked;
- auditable;
- replaceable;
- independently testable;
- unable to mutate canonical identity/state through UI shortcuts.

## Evolution rule

No identity change may be created from a random value, a UI animation, or a
single unvalidated model output. A durable evolution record requires evidence,
reason, provenance, previous version, new version, timestamp and policy
approval.

## Reality rule

A local unit test proves code behavior. It does not prove Railway, PostgreSQL,
Android, OS lifecycle, or multi-day continuity. Those require real deployment
validation.

## Visual Presence Invariant (S6V)

**Visual Presence is a projection of the Entity, never an authority over the Entity.**

The Living Visual Entity may render, animate, express presentation state, adapt to performance/accessibility constraints, and communicate canonical presence. It may not create or mutate identity, memory, bond, trust, emotion, curiosity, continuity, goals, intentions, life intentions, constitution, or actions.

Light and Dark themes are the same entity and the same visual contract. Performance tiers and reduced-motion behavior are presentation policies only.
